## 競賽規則帶來的限制

- **不得使用中國或中資的開源模型（例如 DeepSeek）或介接工具（API、MCP 等）**，訓練和推論都不行。我們使用的 YOLO（Ultralytics）和 Claude API 不在此限，但**新增任何模型或套件前都要先確認來源**（見 ADR-0005）。
- 有使用生成式 AI 工具、第三方素材或公開資料，**都要在作品說明書中揭露使用方式和來源**，開發時用的 AI 輔助工具也包括在內。
- 須遵守肖像權和個資保護規定：**錄影時入鏡的同學要簽同意書**。
- 作品不能已經商品化或量產。

## 分工原則

| 角色 | 負責範圍 | 主要分支 |
|---|---|---|
| **A：MES／整合** | 資料模型、Flask API、時間計算、所有網頁、回填、工作模式指標、整合與 Demo | `feature/mes-core`、`feature/dashboard`、`feature/analytics` |
| **B：AI／影像** | YOLO pose 判定、作業區設定、在場人數、事件傳送程式、骨架片段、影片錄製、準確度評估、LLM 效率建議 | `feature/vision`、`feature/advice` |

- 兩人唯一的接點是 **AI 事件 API 合約**（`docs/api.md`）。第 1 週先定稿，之後雙方各自開發：A 用模擬器測試，B 用合約規定的 JSON 格式測試。
- 每個功能開一個分支，透過 PR 合併到 `main`，由另一人 review。
- 每週日晚上同步一次：展示本週成果，並調整下週工作。

## 各階段工作

### 階段 0：合約與基礎（W1）

**A**
- [ ] 撰寫 `docs/api.md`：狀態事件（工作站、狀態、在場人數、時間）、心跳、骨架片段上傳的格式，和 B 一起定稿
- [ ] 改寫資料表：作業員、工作站（含門檻設定）、產品（每件標準工時）、工單（數量、實際完成總數、四種工單狀態）、作業段（完成件數）、工作狀態事件（以工作站為單位）、心跳
- [ ] 建立種子資料：3 個作業員、2 個工作站、2 種產品、數張工單
- [ ] 程式和 README 統一改用新名詞，移除「暫停」「異常」

**B**
- [ ] 建立 YOLO pose 環境，能在筆電 webcam 和影片檔上畫出骨架
- [ ] 寫拍攝腳本，錄第一批模擬影片：作業中、滑手機、發呆、離開、兩人協作、遮擋鏡頭
- [ ] 設計作業區的設定格式，例如每個工作站一個 JSON，記錄多邊形座標

### 階段 1：主流程 MVP（W2–W3）

**A**
- [ ] 工作站頁 `/station/<id>`：掃員工證 → 掃工單 → 開始作業段；結束時填完成件數；完成工單時確認實際完成總數。掃碼先用網址參數模擬，再接手機相機掃 QR code
- [ ] 狀態事件 API 和心跳 API；心跳逾時記為「無法判斷」
- [ ] 時間計算：狀態事件 → 時間區間 → 每個作業段的有效工時、在場閒置、離開、無法判斷；協作時以人時加總
- [ ] 自動結束（時間回溯到最後一次看到人）；在場人數多於掃碼人數時標示未登記協助
- [ ] **AI 模擬器腳本**：依照合約定時送出隨機狀態事件，讓 A 不必等 B 就能開發
- [ ] 主管看板改版：每張工單的有效工時、閒置、無法判斷、效率；各工作站的即時狀態

**B**
- [ ] 規則判定：手腕關鍵點在作業區內且持續有動作 → 作業中；有人但不符合條件 → 在場閒置；沒有人 → 離開；偵測失敗 → 無法判斷
- [ ] 平滑處理（數秒內多數決），只在狀態改變時送事件，每 5 秒送一次心跳
- [ ] 計算在場人數
- [ ] 事件傳送程式，依照合約打 MES 的 API

### 階段 2：真實 AI 串接（W4–W5）

**A**
- [ ] 作業員個人頁，只顯示自己的作業段和數據
- [ ] 回填出口：工單工時的 API 和 CSV 匯出，和內部工單資料表分開（見 ADR-0003）
- [ ] 骨架片段的儲存和檢視頁，給主管處理申訴；超過 7 天自動清除
- [ ] 每個工作站的門檻設定頁

**B**
- [ ] 實機串接：webcam 或影片 → AI → MES，修正端到端的問題
- [ ] 產生骨架片段：狀態改變前後數秒的關鍵點序列，上傳給 MES
- [ ] **準確度評估**：替錄好的影片標上正確答案，算出混淆矩陣和準確率，當作報告素材
- [ ] 視準確度決定是否訓練分類模型補強（ADR-0004 的第二步，可以延到 W6）

### 階段 3：進階分析（W6）

**A**
- [ ] 計算工作模式指標：每件有效工時、閒置比例、中斷次數、平均連續作業長度、單人或協作
- [ ] 找出標竿：同一產品中，至少有 3 個作業段的作業員裡，每件有效工時中位數最低的人
- [ ] 效率比較頁：主管看得到實名，看板以標竿為比較基準

**B**
- [ ] 效率建議模組：把指標和差距交給 LLM（Claude API）產生建議，要求只能引用提供的數字；LLM 無法使用時改用範本
- [ ] 提供一支 API 讓 A 的頁面呼叫

## 主要風險與對策

| 風險 | 對策 |
|---|---|
| 「作業中」和「在場閒置」判斷不準 | 先用規則版本求穩定；Demo 影片挑動作明確的情境；準確度如實寫進報告，並列出改進方向 |
| A、B 進度互相卡住 | W1 定好 API 合約；A 用模擬器、B 用合約格式各自開發；M1 前不需要真實串接 |
| 進階分析沒有資料可以展示 | W7 刻意錄出不同的工作模式；種子資料準備好歷史作業段 |
| 需要 LLM API 金鑰和費用 | 範本備案確保沒有網路也能 Demo；金鑰放在 `.env`，不要 commit |
| 線上展示形式不清楚 | 寄信問主辦單位（aittc.nutn@gmail.com）；同時準備即時 Demo 和錄影兩種版本 |
| 誤用不合規的模型或套件 | 新增依賴時檢查來源（ADR-0005）；作品說明書揭露所有 AI 工具 |
| 決賽現場網路或設備出狀況 | 全系統可在單一筆電離線執行；準備備援影片 |
